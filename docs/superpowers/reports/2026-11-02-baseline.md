## What `--fake` measures

The production build (`npm run build`, Nitro Vercel preset) served locally by `e2e/perf/serve-ts.mjs`: the same `.vercel/output/functions/__server.func/index.mjs` fetch handler Vercel runs, on srvx (the server Nitro is built on), plus `.vercel/output/static` with the immutable `/assets/**` header. Not `vite dev`, not `vite preview`. OpenAI is replaced by the fake Responses server (`go/cmd/fakeopenai`, fixture `stream`: 6-rune chunks every 30 ms) with `OPENAI_API_KEY=test`; the harness aborts if a counted translation does not reach the fake, and fails a settled-page run that makes more than one upstream request. `--app go` builds the Go app with `go build` and fails clearly while it does not serve the translator page.

Consequences to keep in mind when reading the numbers:

- **One compression policy.** Local servers send everything uncompressed for every app; compare the computed `gzip -9` rows for size. Production compression shows up only in `--live`, where each resource's `content-encoding` is recorded.
- **Fonts and third parties are blocked for every app.** Each browser gets a proxy setting pointing at a closed port with loopback bypassed, so third-party requests (the TS app's Pretendard fonts from jsDelivr) fail fast; and every request reaches the app through `e2e/perf/gateway.ts`, a pass-through that answers every font request (`Sec-Fetch-Dest: font` or a font file extension) with 404, so a same-origin font (as the Go app may serve) is blocked the same way. Text renders in the system font; FCP/LCP here therefore exclude web-font work that the live trace below shows ending at 3.4-3.8 s. The gateway streams responses chunk by chunk and propagates aborts (unit-tested).
- **Translation timings are fake-paced.** They are the client debounce (400 ms, see below) + app/server overhead + the fake's fixed pacing (+ the simulated network on throttled profiles), not OpenAI latency. With real OpenAI, latency is dominated by the model; expect small gains there.
- **Build provenance.** The JSON records a sha256 over the whole `.vercel/output` (Go: the binary), the hashed asset names, and a sha256 prefix per served JS/CSS/HTML body; `--skip-build` is allowed for experiments but is recorded and shown next to the build hash.

**Network throttling (`e2e/perf/throttle-proxy.ts`)** replaces Chromium's CDP network emulation, which (a) does not exist for WebKit and (b) let the navigation's own document through unthrottled (the first baseline measured `responseStart` ~4 ms and the HTML in ~0 ms while subresources started at ~582 ms). The proxy is one simulated access link shared by every connection of the page: Lighthouse mobile values (RTT 150 ms x 3.75 = 562.5 ms, 1.6 Mbps x 0.9 down, 750 Kbps x 0.9 up), each 1460-byte segment waits for the shared link (FIFO by arrival), takes size/bandwidth, then arrives RTT/2 later; a new TCP connection pays one extra RTT (handshake) before its first byte enters the link, and that wait is per connection, so it never delays requests on connections that are already open. It is hand-written because the maintained options throttle per connection (Toxiproxy toxics, Node stream throttles: six browser connections would get six times the bandwidth) or shape the whole OS network with root (`@sitespeed.io/throttle`). In `--fake` it forwards transparently to the gateway; in `--live` it is the browser's HTTP CONNECT proxy: the CONNECT request and its `200 Connection Established` are answered directly (proxy plumbing a direct connection does not have), and only the tunnelled TLS/HTTP bytes cross the link (checked against https://example.com in both engines). Unit tests (`e2e/perf/throttleProxy.test.ts`) cover: handshake + one RTT for a new connection, one RTT per later exchange, an open connection not waiting while another handshakes, CONNECT answered in < 50 ms with tunnelled bytes throttled, and downstream bandwidth shared between connections. Verification in the browser:

- Node fetch of the 361 KB `index` chunk through the proxy: headers after 1235 ms (2 RTT + server), body done at 3060 ms (expected ~1913 ms of link time after the headers).
- Document transfer (`responseEnd - responseStart`) now matches the link: 83 ms measured vs 90 ms expected for 16.6 KB (rows "Document transfer" below).
- Throttled TTFB = handshake RTT + request RTT + server ≈ 1140 ms with no TLS; production adds a real TLS round trip.

## How each metric is measured

Every run starts in a fresh browser context (empty cache, no cookies, service workers blocked, `en-US`). Per profile and iteration: one load run (cold + repeat visit), one interaction run, one diagnostic probe run. Before the first profile a discarded warm-up load + interaction lets the freshly started server load its lazy chunks.

- **TTFB, DOMContentLoaded, load, document transfer**: Navigation Timing (`responseStart`, `domContentLoadedEventEnd`, `loadEventEnd`, `responseEnd - responseStart`), ms from navigation start. "Document transfer expected" = the document's transferred bytes / link bandwidth.
- **FCP / LCP / CLS / long tasks**: `PerformanceObserver`s installed by an init script before any page script. WebKit has no `layout-shift` or `longtask` entries, so its CLS and TBT are n/a (`supportedEntryTypes` is recorded per profile).
- **TBT**: Lighthouse-style, the sum over long tasks of the time after FCP beyond 50 ms, observed until 1 s after network idle (Chromium only).
- **Bytes**: from the page load's responses, classified by content type. Raw = decoded body; gzip = `gzip -9` of the decoded body; transferred = same-origin Resource Timing `transferSize` (headers + encoded body, 0 for an HTTP cache hit; cross-origin falls back to Playwright's sizes). Playwright's own `request.sizes()` is not used for transfer: for cache hits Chromium reports negative sizes and WebKit the full size. **Inline code** is counted from the served HTML parsed with parse5: executable inline `<script>` (no `type`, `module`, JavaScript MIME types) and event-handler attributes (`on*`, htmx `hx-on:*`/`hx-on::*`/`hx-on-*`) as inline JS, `<style>` as inline CSS, other `<script>` types (JSON, import maps) as inline data. **JS total = external + inline** is the deciding JS size. "JS loaded through done" sums every JS body (plus the document's inline JS) the interaction page loaded from navigation until the settled-page translation completed, so code fetched lazily on first interaction counts.
- **Repeat visit**: after the cold load settles, a second navigation in the same context (warm HTTP cache, cookies kept), measured the same way; the interaction run also repeats typing at first focus on a second navigation.
- **Typing during load**, presented per profile in three layers:
  1. **Input kept from** (headline app property) = max(FCP, earliest kept keystroke) from the space probe below: from this moment typed text stays in the field; whether it is acted on is the gate below.
  2. **Gate: typing at first focus wiped / ignored**: the page is opened and, at the first moment the textarea can take focus, one real sentence (`[fx:stream] <nonce> How are you doing today, my friend?`, ending in `?`) is typed as one burst, then nothing. It counts only if its text is still in the field after the page settles (network idle + 500 ms) **and** the upstream receives a translation of exactly that text and the full fixture main text appears with no further input (3 s grace after settle). Otherwise it is _wiped_ (the field no longer holds it) or _ignored_ (it does, but nothing was translated). The rate is a gate: a page that loses early input fails it whatever its timings. The row "wiped and the remainder translated" counts runs where the surviving tail of a wiped burst was sent upstream as a request of its own.
  3. **Secondary: first typeable incl. the retype model** = max(FCP, earliest kept keystroke, earliest acted-on keystroke) for the burst, where a dropped burst is handled as a user would: after settle, Clear (the app's button) and type a fresh sentence, the penalty included. The row "of which harness wait" (settle point minus "input kept from") states how much of it is the harness's model of a user noticing the loss rather than app time; "nav start to first main char" follows the translation that counted.
- **Diagnostics (space probe)**: a separate run types a space whenever the textarea takes focus during load, until network idle + 5 tries. "Earliest kept keystroke" is the earliest space still in the field afterwards (the moment the field stops being reset), "shown" the earliest input event at all; the probe also checks that whitespace-only input causes **no** upstream request. The earliest kept keystroke (with the probe run's FCP) is the headline "input kept from"; the other rows are diagnostics. A space proves the field keeps text, not that the app acts on it: acting is what the burst gate checks.
- **Translation on the settled page**: Clear, fill all but the last 6 characters, type those 60 ms apart. An in-page `MutationObserver` stamps `performance.now()` when `[data-testid="main-translation"]` first shows text and when the main Copy button enables, relative to the last `input` event. **Done** is app-agnostic (the stage-2 Go app has no Listen button): Copy enabled, main text present, no fetch/XHR/EventSource request that started after the last keystroke still in flight and at least one finished (Playwright request events, tracked outside the page, so a response still open is seen), and no DOM change outside `<head>` for 500 ms after the latest of Copy, the last DOM change and the last request end; done = that latest time. DOM quiet alone is not enough: the TS app renders nothing for ~2.5 s while learner details stream after main. The row "request end minus last DOM change" shows a response held open after the page stopped changing (e.g. an SSE response not closed after its final event); the time the TS app's Listen button enables is kept as a diagnostic and matches done. Both apps use the 400 ms sentence-final debounce here, included in every number. "First main char" is DOM text present, not a paint.
- **Keyboard (mobile profiles), two modes**, both imitating the browser's own scroll-to-focused-field identically for every app. The source is focused as a tap would (caret at the end). _visualViewport shrink_ (overlays-content keyboards: iOS Safari, Android default): `window.visualViewport` is replaced by an `EventTarget` that mirrors the real one until overridden (the technique of `tests/browser/mobile.browser.tsx`); its height shrinks in 50 px steps 50 ms apart to 50 % of the window with `resize` + `scroll` on every step; after each step, if the caret line (mirror-element measurement) is not inside the visible band, the visual viewport pans so it is: `offsetTop = clamp(caretBottom - visibleHeight + 16, 0, layoutHeight - visibleHeight)` (or `caretTop - 16` when the caret is above the band); a visible caret keeps the current offset. _Layout viewport resize_ (resizes-content): `page.setViewportSize` shrinks the real viewport in the same steps, and after each step the focused textarea is scrolled into view (`scrollIntoView({ block: 'nearest' })`, a no-op when it is visible or nothing scrolls). Each mode reports the final pan offset (visual mode), the sum of `layout-shift` values during the shrink (Chromium only; not the Web Vitals session-window CLS), the absolute top change of the main text and the source textarea, and whether, afterwards, the main text's first line, the textarea and the caret line lie inside the visible band `[offsetTop, offsetTop + height]` and the textarea keeps focus. **dy is not "lower is better"**: a layout that does not react to the keyboard can have dy 0 and rely on the browser's pan; read dy with the visibility rows.
- **Server cold vs warm TTFB**: Node HTTP client, no browser; the app process is restarted per sample, cold = first `GET /` after the port accepts TCP, warm = the second.

## Observations

All 120 runs succeeded (10 load + 10 repeat load + 10 interaction + 10 probe per profile). Settled-page translations made exactly one upstream request each and showed the full fixture text; whitespace-only input never reached the upstream. The run's commit shows "(dirty)" only because other agents had uncommitted work under `go/` at the time; `e2e/perf` (harness hash above) and the TS app sources were clean, and the TS build was rebuilt for the run.

- **Client JS is the dominant cost**: 285.3 KiB gzip total (283.7 KiB external in two chunks + 1.6 KiB inline), 907.4 KiB decoded; no further JS is loaded through the first translation. CSS 28.7 KiB gzip. The Go app's budget is 40 KiB gzip of JS including htmx.
- **Typing during load, per profile** (read the three layers together; the MacBook headline never alone):

  | Profile                          | Input kept from (headline) | Gate: typing at first focus wiped (cold / repeat) | Secondary: first typeable incl. retype model | of which harness wait |
  | -------------------------------- | -------------------------- | ------------------------------------------------- | -------------------------------------------- | --------------------- |
  | iPhone WebKit, slow 4G           | 7463 ms                    | 10/10 / 10/10                                     | 9074 ms                                      | 1562 ms               |
  | Pixel Chromium, 4x CPU + slow 4G | 8149 ms                    | 10/10 / 10/10                                     | 9776 ms                                      | 1539 ms               |
  | MacBook Chromium                 | 86 ms                      | **10/10** / 0/10                                  | 1188 ms                                      | 1043 ms               |

  The SSR textarea takes focus at FCP (iPhone 2.56 s, Pixel 3.19 s, MacBook 0.05 s), but React's hydration resets the controlled field, so text typed before hydration is lost on every cold load, on every profile; the field keeps input only from the headline moment on. On the MacBook the window is short (hydration ~90 ms after navigation) but a user who starts typing at first paint still loses it 10/10. Under the retype model the user notices at the settle point and retypes; that harness wait is 1.0-1.6 s of the secondary number, so when comparing with the Go app use the headline and the gate first.

- **Product finding (confirmed): typing during hydration bills a truncated sentence.** When hydration wipes only the first part of the burst, the part typed after hydration is translated as a real request: iPhone repeat visits 5/10, MacBook cold loads 2/10 (earlier runs of the same harness: iPhone repeat 8-10/10). On production that is a billed OpenAI translation of a fragment, triggered by normal typing, before the user's real request.
- **Repeat visits** (warm cache, 0 JS bytes transferred): Pixel FCP 0.62 s, input still wiped 10/10 (first typeable incl. retype 2.53 s); iPhone FCP 1.17 s, wiped 10/10 (3.5 s); MacBook keeps and translates the burst 10/10 (~41 ms, first main char 0.79 s; one earlier run of the same harness lost it 1/10, the warm-cache hydration window is ~40 ms). WebKit's repeat TTFB (1140 ms) includes a new-connection RTT that Chromium (581 ms) avoids by reusing its connection.
- **Translation on the settled page**: last key to first main char 0.67 s on MacBook (400 ms debounce + app/server + fake pacing) and 1.25-1.26 s on the throttled profiles (one RTT each way through the proxy); Copy follows ~300 ms later (the main JSON string must close). "Done" is 4.7-5.3 s, the fake fixture's full stream length; the translation request ends 5-35 ms before the last DOM change in every run ("request end minus last DOM change" negative: no response held open).
- **Keyboard**: in both modes the main text's first line, the textarea and the caret stay visible and the textarea keeps focus, 10/10 on both mobile profiles. The app re-lays itself out to the visible height, so the scroll-to-caret model never needed to pan (final offsetTop 0). Movement: main text 99 px (iPhone) / 58 px (Pixel), textarea 323 / 413 px in both modes; layout-shift sum on Pixel 0.265 (visual) and 0.504 (resize). Deterministic. The editor moving up is intended (it stays above the keyboard), so dy is context, not a score.
- **Network check**: document transfer 90 ms against 91 ms expected on the link, TTFB ≈ 1140 ms ≈ 2 RTT + server on both throttled profiles.
- **Cold server start**: first request 90 ms vs 4 ms warm (local Node; Vercel cold starts add instance boot and are only visible in `--live`).
- `/_vercel/insights/script.js` is requested from the app origin and 404s locally (the analytics script exists only on Vercel); it counts as 0 bytes here.
