## What `--fake` measures

The production build (`npm run build`, Nitro Vercel preset) served locally by `e2e/perf/serve-ts.mjs`: the same `.vercel/output/functions/__server.func/index.mjs` fetch handler Vercel runs, on srvx (the server Nitro is built on), plus `.vercel/output/static` with the immutable `/assets/**` header. Not `vite dev`, not `vite preview`. OpenAI is replaced by the fake Responses server (`go/cmd/fakeopenai`, fixture `stream`: 6-rune chunks every 30 ms) with `OPENAI_API_KEY=test`; the harness aborts if a counted translation does not reach the fake, and fails a settled-page run that makes more than one upstream request. `--app go` builds the Go app with `go build` and fails clearly while it does not serve the translator page.

Consequences to keep in mind when reading the numbers:

- **One compression policy.** Local servers send everything uncompressed for every app; compare the computed `gzip -9` rows for size. Production compression shows up only in `--live`, where each resource's `content-encoding` is recorded.
- **Third-party requests are blocked for every app.** Each browser gets a proxy setting pointing at a closed port with loopback bypassed, so CDN fonts (Pretendard from jsDelivr) and `/_vercel/insights` analytics fail fast; text renders in the system font. FCP/LCP here therefore exclude web-font work that the live trace below shows ending at 3.4-3.8 s.
- **Translation timings are fake-paced.** They are the client debounce (400 ms, see below) + app/server overhead + the fake's fixed pacing (+ the simulated network on throttled profiles), not OpenAI latency. With real OpenAI, latency is dominated by the model; expect small gains there.
- **Build provenance.** The JSON records a sha256 over the whole `.vercel/output` (Go: the binary), the hashed asset names, and a sha256 prefix per served JS/CSS/HTML body; `--skip-build` is allowed for experiments but is recorded and shown next to the build hash.

**Network throttling (`e2e/perf/throttle-proxy.mjs`)** replaces Chromium's CDP network emulation, which (a) does not exist for WebKit and (b) let the navigation's own document through unthrottled (the first baseline measured `responseStart` ~4 ms and the HTML in ~0 ms while subresources started at ~582 ms). The proxy is one simulated access link shared by every connection of the page: Lighthouse mobile values (RTT 150 ms x 3.75 = 562.5 ms, 1.6 Mbps x 0.9 down, 750 Kbps x 0.9 up), each 1460-byte segment waits for the shared link, takes size/bandwidth, then arrives RTT/2 later; a new TCP connection pays one extra RTT (handshake). It is hand-written because the maintained options throttle per connection (Toxiproxy toxics, Node stream throttles: six browser connections would get six times the bandwidth) or shape the whole OS network with root (`@sitespeed.io/throttle`). In `--fake` it forwards transparently to the app; in `--live` it is the browser's HTTP CONNECT proxy (TLS tunnelled through the same link; checked against https://example.com in both engines). Verification:

- Node fetch of the 361 KB `index` chunk through the proxy: headers after 1235 ms (2 RTT + server), body done at 3060 ms (expected ~1913 ms of link time after the headers).
- Document transfer (`responseEnd - responseStart`) now matches the link: 83 ms measured vs 90 ms expected for 16.6 KB (rows "Document transfer" below).
- Throttled TTFB = handshake RTT + request RTT + server ≈ 1140 ms with no TLS; production adds a real TLS round trip.

## How each metric is measured

Every run starts in a fresh browser context (empty cache, no cookies, service workers blocked, `en-US`). Per profile and iteration: one load run (cold + repeat visit), one interaction run, one diagnostic probe run. Before the first profile a discarded warm-up load + interaction lets the freshly started server load its lazy chunks.

- **TTFB, DOMContentLoaded, load, document transfer**: Navigation Timing (`responseStart`, `domContentLoadedEventEnd`, `loadEventEnd`, `responseEnd - responseStart`), ms from navigation start. "Document transfer expected" = the document's transferred bytes / link bandwidth.
- **FCP / LCP / CLS / long tasks**: `PerformanceObserver`s installed by an init script before any page script. WebKit has no `layout-shift` or `longtask` entries, so its CLS and TBT are n/a (`supportedEntryTypes` is recorded per profile).
- **TBT**: Lighthouse-style, the sum over long tasks of the time after FCP beyond 50 ms, observed until 1 s after network idle (Chromium only).
- **Bytes**: from the page load's responses, classified by content type. Raw = decoded body; gzip = `gzip -9` of the decoded body; transferred = same-origin Resource Timing `transferSize` (headers + encoded body, 0 for an HTTP cache hit; cross-origin falls back to Playwright's sizes). Playwright's own `request.sizes()` is not used for transfer: for cache hits Chromium reports negative sizes and WebKit the full size. **Inline code** is counted from the served HTML parsed with parse5: executable inline `<script>` (no `type`, `module`, JavaScript MIME types) as inline JS, `<style>` as inline CSS, other `<script>` types (JSON, import maps) as inline data. **JS total = external + inline** is the deciding JS size. "JS loaded through done" sums every JS body (plus the document's inline JS) the interaction page loaded from navigation until the settled-page translation completed, so code fetched lazily on first interaction counts.
- **Repeat visit**: after the cold load settles, a second navigation in the same context (warm HTTP cache, cookies kept), measured the same way; the interaction run also repeats typing at first focus on a second navigation.
- **First typeable (deciding)**: the page is opened and, at the first moment the source textarea can take focus, one real translatable sentence (`[fx:stream] <nonce> How are you doing today, my friend?`, ending in `?`) is typed as one burst, then nothing. The burst counts only if its text is still in the field after the page settles (network idle + 500 ms) **and** a translation of exactly that text reaches the upstream and shows main text with no further input (3 s grace after settle). Otherwise it is _dropped_: **wiped** (the field no longer holds it) or **ignored** (it does, but nothing was translated). A dropped burst is handled as a user would: after settle, Clear (the app's button) and type a fresh sentence; that penalty is included. **First typeable = max(FCP of that run, earliest kept keystroke, earliest acted-on keystroke)**, i.e. the burst's first keystroke when it counted, else the retype's first keystroke. **Nav start to first main char, typing at first focus** = navigation start to the first main character of the translation that counted. For dropped runs the table also shows the harness settle point and the Clear + retype time, so the part of first typeable that is the harness's reaction model (settle, then retype) can be separated from app time.
- **Diagnostics (space probe)**: a separate run types a space whenever the textarea takes focus during load, until network idle + 5 tries. "Earliest kept keystroke" is the earliest space still in the field afterwards (the moment the field stops being reset), "shown" the earliest input event at all; the probe also checks that whitespace-only input causes **no** upstream request. These rows are diagnostics only: a space proves the field keeps text, not that the app will act on it.
- **Translation on the settled page**: Clear, fill all but the last 6 characters, type those 60 ms apart. An in-page `MutationObserver` stamps `performance.now()` when `[data-testid="main-translation"]` first shows text, when the main Copy button enables and when the main Listen button enables (the whole result is done), relative to the last `input` event. Both apps use the 400 ms sentence-final debounce here, included in every number. "First main char" is DOM text present, not a paint.
- **Keyboard (mobile profiles), two modes.** _visualViewport shrink + pan_ (overlays-content keyboards: iOS Safari, Android default): `window.visualViewport` is replaced by an `EventTarget` that mirrors the real one until overridden (the technique of `tests/browser/mobile.browser.tsx`); the source is focused, then the visual height shrinks in 50 px steps 50 ms apart to 50 % of the window, and a final step pans `offsetTop` to 12.5 % of the window (the browser test used 300 of 640 px visible and offsetTop 80), with `resize` + `scroll` on every step. _Layout viewport resize_ (resizes-content): `page.setViewportSize` shrinks the real viewport in the same steps to 50 %. Each mode reports the sum of `layout-shift` values during the shrink (Chromium only; programmatic focus, so not the Web Vitals session-window CLS), the absolute top change of the main text and the source textarea, and whether, afterwards, the main text's first line, the textarea, the caret line (mirror-element measurement) lie inside the visible band `[offsetTop, offsetTop + height]` and the textarea still has focus. **dy is not "lower is better"**: a layout that does not react to the keyboard has dy 0 and hides the editor; read dy with the visibility rows.
- **Server cold vs warm TTFB**: Node HTTP client, no browser; the app process is restarted per sample, cold = first `GET /` after the port accepts TCP, warm = the second.

## Observations

All 120 runs succeeded (10 load + 10 repeat load + 10 interaction + 10 probe per profile). Settled-page translations made exactly one upstream request each, and whitespace-only input never reached the upstream.

- **Client JS is the dominant cost**: 285.3 KiB gzip total (283.7 KiB external in two chunks + 1.6 KiB inline), 907.4 KiB decoded; no further JS is loaded through the first translation. CSS 28.7 KiB gzip. The Go app's budget is 40 KiB gzip of JS including htmx.
- **Typing at first focus is lost in every cold run on every profile.** The SSR textarea takes focus at FCP (iPhone 2.57 s, Pixel 3.22 s, MacBook 0.06 s), but React's hydration resets the controlled field, so the burst is wiped 10/10 times. The diagnostic probe shows when the field starts keeping text: iPhone 7.46 s, Pixel 8.19 s, MacBook 0.10 s. Under the deciding definition the user then clears and retypes once the page has settled, so **first typeable** is iPhone 9.07 s, Pixel 9.82 s, MacBook 1.19 s and **nav start to first main char** iPhone 11.05 s, Pixel 11.71 s, MacBook 1.98 s.
- **How much of first typeable is the harness's reaction model.** For a dropped burst, first typeable = settle point (network idle + 500 ms: iPhone 9.02 s, Pixel 9.70 s, MacBook 1.13-1.64 s) + Clear and retype (50-140 ms). The app-side moment is the probe's earliest kept keystroke; the gap between it and the settle point (iPhone ~1.6 s, Pixel ~1.5 s, MacBook ~1.0-1.5 s) is the harness's model of a user noticing the loss. A page that keeps and acts on the burst (as a server-rendered form without hydration should) scores max(FCP, burst keystroke) instead, so **when comparing with the Go app, read first typeable together with the "wiped" and "settle point" rows and the probe diagnostics**, not alone.
- **Product finding (confirmed in the data): typing during hydration bills a truncated sentence.** When hydration wipes only the first part of the burst, the remainder that was typed after hydration is translated as a real request: iPhone repeat visits 10/10, MacBook cold loads 3/10 ("Wiped and the remainder translated" rows). On production that is a billed OpenAI translation of a fragment, triggered by normal typing, before the user's real request.
- **Repeat visits** (warm cache, 0 JS bytes transferred): Pixel FCP 0.62 s and first typeable 2.58 s (still wiped 10/10); iPhone FCP 1.17 s, first typeable 3.55 s (wiped 10/10); MacBook keeps and translates the burst (first typeable 43 ms, first main char 0.81 s). WebKit's repeat TTFB (1146 ms) includes a new-connection RTT that Chromium (587 ms) avoids by reusing its connection.
- **Translation on the settled page**: last key to first main char is 0.67 s on MacBook (400 ms debounce + app/server + fake pacing) and 1.24-1.27 s on the throttled profiles (one extra RTT each way through the proxy); Copy follows ~300 ms later (the main JSON string must close); "done" (4.6-5.3 s) is the fake fixture's full stream length.
- **Keyboard**: both modes keep the main text's first line, the textarea and the caret visible and the textarea focused, 10/10 on both mobile profiles. Movement: visualViewport shrink + pan moves the main text 17 px (iPhone) / 47 px (Pixel) and the textarea 241 / 308 px; layout viewport resize moves them 99 / 58 px and 323 / 413 px; layout-shift sums on Pixel 0.331 and 0.504. These are deterministic (identical in every run). The editor moving up is the intended behaviour (it stays visible above the keyboard), so dy is context, not a score.
- **Network check**: document transfer 83-84 ms against 91 ms expected on the link, TTFB ≈ 1145 ms ≈ 2 RTT + server on both throttled profiles: the proxy throttles the document like everything else.
- **Cold server start**: first request 95 ms vs 5 ms warm (local Node; Vercel cold starts add instance boot and are only visible in `--live`).
- `/_vercel/insights/script.js` is requested from the app origin and 404s locally (the analytics script exists only on Vercel); it counts as 0 bytes here.
