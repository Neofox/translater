## What `--fake` measures

The production build (`npm run build`, Nitro Vercel preset) served locally by `e2e/perf/serve-ts.mjs`: the same `.vercel/output/functions/__server.func/index.mjs` fetch handler Vercel runs, on srvx (the server Nitro is built on), plus `.vercel/output/static` with the immutable `/assets/**` header. Not `vite dev`, not `vite preview`. OpenAI is replaced by the fake Responses server (`go/cmd/fakeopenai`, fixture `stream`: 6-rune chunks every 30 ms) with `OPENAI_API_KEY=test`; the harness aborts if a translation does not reach the fake, and fails a run that makes more than one upstream request. `--app go` builds the Go app with `go build` and fails clearly while it does not serve the translator page.

Consequences to keep in mind when reading the numbers:

- **Loopback network.** TTFB and the unthrottled profiles' FCP/LCP are local-process numbers. They are for app-vs-app comparison on equal terms, not production latency (that is the live section below).
- **No compression locally, for every app.** Local servers send everything uncompressed (one policy, so neither app gets a local advantage); compare the computed `gzip -9` rows for size. Production compression (Vercel brotli/gzip) only shows up in `--live`, where each resource's `content-encoding` is recorded.
- **Translation timings are fake-paced.** "Last key to ..." numbers are the client debounce (400 ms, see below) + app/server overhead + the fake's fixed pacing. They measure the app's own overhead, not OpenAI. With real OpenAI, latency is dominated by the model; expect small gains there.
- `/_vercel/insights/script.js` is requested and 404s locally (the analytics script exists only on Vercel); it counts as 0 bytes here and will be counted in `--live`.
- Font CSS/subsets load from their CDN over the real network, as in production.

## How each metric is measured

Every run uses a fresh browser context (empty cache, no cookies, `en-US`). Per profile, each of the 10 iterations does one page-load run and one interaction run (separate contexts). Before the first profile, a discarded warm-up load + interaction lets the freshly started server load its lazy chunks.

- **TTFB, DOMContentLoaded, load**: Navigation Timing (`responseStart`, `domContentLoadedEventEnd`, `loadEventEnd`), ms from navigation start. Chromium's CDP network emulation does not delay the navigation's `responseStart`, so the Pixel TTFB excludes the emulated 562.5 ms latency (verified: `responseStart` ~4 ms, subresources start at ~582 ms); FCP and everything later include the throttled delivery.
- **FCP / LCP / CLS / long tasks**: `PerformanceObserver`s installed by an init script before any page script (`paint`, `largest-contentful-paint`, `layout-shift`, `longtask`, buffered). WebKit has no `layout-shift` or `longtask` entries, so its CLS and TBT are n/a (the JSON records `supportedEntryTypes` per profile).
- **TBT**: Lighthouse-style, the sum over long tasks of the time after FCP beyond 50 ms, observed until 1 s after network idle (Chromium only).
- **JS / CSS / HTML bytes**: from the page load's network responses. Raw = decoded body length; transferred = body bytes on the wire (`request.sizes().responseBodySize`); gzip = `gzip -9` of the decoded body (encoding-independent). "All transferred" adds every response's body + headers (fonts, favicon, ...).
- **First typeable**: from `commit` on, the harness focuses the textarea whenever it can and types a space, until network idle + 5 more tries. An init script records the timestamp of every `input` event on the textarea. A keystroke counts only if its character is still in the field after the page settles (whitespace never triggers a translation). **First typeable** = the earliest surviving keystroke; **first keystroke shown** = the earliest `input` event at all, which hydration may later wipe.
- **Last key to first main char / Copy enabled / done**: an in-page `MutationObserver` (the pattern of the e2e suite's `recordResult`) stamps `performance.now()` when `[data-testid="main-translation"]` first shows non-empty text, when the main `[data-testid="output-toolbar"] [data-testid="copy-button"]` becomes enabled, and when the main Listen button becomes enabled (the whole result is done: Listen enables only then). Times are relative to the `timeStamp` of the last `input` event. The source is `"[fx:stream] <nonce> How are you doing today, my friend?"`: everything but the last 6 characters is filled, those are typed 60 ms apart. It ends in `?`, so **both apps use the 400 ms sentence-final debounce**, which is included in every one of these numbers. "First main char" is DOM text present, not a paint.
- **Keyboard open (mobile profiles)**: an init script replaces `window.visualViewport` with an `EventTarget` that mirrors the real one until overridden (the technique of `tests/browser/mobile.browser.tsx`). After the translation, the harness blurs the source, waits 400 ms, then focuses it (`preventScroll`) and shrinks the visual viewport height in 50 px steps, 50 ms apart, down to 60 % of the window, firing `resize` and `scroll` on each step. Reported: the CLS of `layout-shift` entries during the shrink (Chromium only), and the absolute change of the main text's and the source textarea's `getBoundingClientRect().top`.
- **Server cold vs warm TTFB**: a Node HTTP client (new connection each), no browser. The app process is restarted for each of the 10 samples; cold = the first `GET /` after the port accepts TCP (no HTTP readiness probe, so the lazy SSR chunk import is inside the cold sample), warm = the second `GET /`.

## Observations

- **Client JS is the dominant cost**: 903.8 KiB decoded / 283.7 KiB gzip -9 in two scripts (`index` 116.6 KiB gz, `routes` 173.9 KiB gz), plus 28.7 KiB gz CSS. The Go app's budget is 40 KiB gzip of JS including htmx.
- **Throttled mobile first typeable is 7.9 s**, although the textarea shows keystrokes from ~2.8 s (SSR markup at FCP): characters typed before hydration are reset by the React controlled component, so the first keystroke that survives comes after ~904 KiB of JS has downloaded at ~1.4 Mbps and executed at 4x CPU. Unthrottled it is 90-154 ms.
- **Translation overhead**: last key to first main char is ~680 ms unthrottled = 400 ms debounce + ~280 ms of app, server and fake pacing; Copy follows ~300 ms later (the main JSON string must close). On the throttled Pixel, first char and Copy coincide at ~1014 ms (the main text lands in one rendered update). "Done" (~4.7 s) is the fake fixture's full stream length.
- **Keyboard open**: on Pixel/Chromium, CLS 0.228 during the shrink; the main text moves 56-58 px and the source textarea 258-330 px (the stacked layout re-flows to the visible height). The values were identical in all 10 runs, as expected for a deterministic simulation.
- **Cold server start**: first request 97 ms vs 5 ms warm (local Node; Vercel cold starts add instance boot and are only visible in `--live`).
